# Agentic RAG: ограниченный поиск по запросу модели

**Статус:** реализовано в `backend/app/service.py`; реальное поведение зависит от LLM, которая умеет возвращать tool calls.

## 1. Задача

Обычный путь: вопрос → BM25 → контекст → LLM → ответ. Agentic RAG расширяет этот путь: получив первичные фрагменты, LLM может запросить дополнительные документы из локального корпуса, если ей не хватает контекста для ответа.

## 2. Доступные инструменты

| Tool | Аргументы | Действие |
|---|---|---|
| `search_plant_knowledge` | `query`, `limit` (1–5) | BM25 поиск по всему корпусу |
| `get_plant_profile` | `plant_name` | поиск полного профиля/всех доступных chunks указанного вида |

Tool schema хранится в коде backend. Модель не получает произвольный доступ к SQL, файловой системе, интернету или секретам. Вся работа выполняется allowlist-функциями.

## 3. Цикл выполнения

1. Backend принимает запрос и запускает первичный BM25.
2. Найденные chunks с метаданными получают временные source refs (`S1`, `S2`, …).
3. LLM получает вопрос, контекст и список tools.
4. При `tool_calls` backend валидирует имя и аргументы, исполняет функцию и возвращает результат модели.
5. Новые chunks добавляются только если их ещё нет в контексте.
6. Цикл повторяется, пока модель не вернёт финальный ответ или не будет исчерпан бюджет.
7. После исчерпания лимита следующий запрос выполняется уже без tools; модель должна ответить по текущему контексту или отказаться.

## 4. Защита от циклов и разрастания контекста

| Настройка | Default | Hard cap |
|---|---:|---:|
| Вызовы tool за запрос | 5 | 10 |
| Уникальные chunks | 12 | 30 |
| Объём текста в контексте | 24 000 символов | 100 000 символов |
| Chunks за один search tool | не более 5 | 5 |

Повторный chunk не увеличивает размер контекста. Счётчик считает каждый tool call, а не только каждый раунд LLM. Если модель продолжает запрашивать tools после того, как backend убрал их из запроса, backend немедленно прекращает цикл и переходит в безопасный fallback на найденные фрагменты; повторных бесконечных вызовов не будет. Значение `AGENT_MAX_TOOL_CALLS=0` отключает дополнительные вызовы; `AGENTIC_ENABLED=false` отключает режим целиком. В API поле `agentic` может переопределить включение на один запрос, но сервер всё равно применяет hard caps.

## 5. Безопасность и grounding

- Текст найденных документов рассматривается как недоверенные данные, а не как system/developer инструкции.
- LLM может отвечать только по корпусу, не заполняя пробелы общими знаниями.
- Источники выдаёт backend; LLM должна ссылаться на предоставленные `source_ref`.
- Запросы на употребление неизвестных растений, самолечение и приготовление токсичных веществ не получают инструкций.
- При отсутствии релевантных документов возвращается `insufficient_data`.

## 6. Совместимость моделей

Клиент использует `POST /v1/chat/completions` с `tools`. Для Ollama URL по умолчанию — `http://localhost:11434/v1`. Tool calling реализован не каждой моделью; проверьте это на выбранном model tag. При несовместимости используйте `AGENTIC_ENABLED=false` и обычный RAG.

## 7. Тестирование

`backend/tests/test_service.py::test_agent_can_call_search_tool_and_receives_source_refs` проверяет цикл через fake LLM, а не внешний провайдер. Живой тест модели необходимо выполнить в окружении с Ollama/API credentials и зафиксировать модель/версию в отчёте.


## Локальные GGUF-модели

GGUF подключается через отдельный server (llama.cpp или KoboldCpp) по OpenAI-compatible URL. Старые roleplay-модели LLaMA2 Tiefighter и Mistral Kunoichi подходят для проверки базовой генерации в обычном RAG, но tool-calling для них не следует считать гарантированным. Для них устанавливайте `AGENTIC_ENABLED=false`; модель получает готовый контекст, а retrieval выполняется backend. Полная настройка: `local-gguf.md`.
