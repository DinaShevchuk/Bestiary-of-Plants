# Спецификация корпуса документов

**Статус:** JSONL/SQLite схемы и загрузчики реализованы; пользовательскую SQLite/xlsx пару необходимо проверить после получения самих файлов.

## 1. Принципы корпуса

- У записи стабильный уникальный `document_id`.
- Первичный источник и условия использования должны сохраняться; не добавляйте несуществующие URL.
- Русские и научные названия, aliases и категории индексируются вместе с текстом.
- Токсичность, съедобность, лечебные свойства и иные safety-sensitive факты требуют авторитетного источника и экспертной проверки.
- Демонстрационные и непроверенные записи явно помечаются `record_status=demo_unverified`.
- Полный корпус должен проходить проверку дублей, пустых текстов, кодировки и полноты метаданных.

## 2. Формат исходной записи

Файл `data/plants.jsonl`: одна JSON-запись на строку, UTF-8. Минимальный пример:

```json
{
  "document_id": "plant-0001",
  "plant_name": "Венерина мухоловка",
  "scientific_name": "Dionaea muscipula",
  "aliases": ["дионея"],
  "category": ["хищное растение"],
  "content": "Проверенный текст из источника...",
  "source_title": "Название публикации",
  "source_url": "https://real-source.example/path",
  "publisher": "Автор или организация",
  "published_at": null,
  "accessed_at": "2026-11-20",
  "language": "ru",
  "license_or_usage_note": "Условия использования",
  "record_status": "reviewed"
}
```

URL выше иллюстрирует формат, это не адрес готового источника; используйте только реальные URL. Поля `document_id`, `plant_name`, `content` обязательны. Дополнительные поля могут отсутствовать; неизвестное значение научного названия или URL задаётся `null`, а не догадкой.

## 3. Реализованные этапы обработки

Загрузка JSONL: `backend/app/corpus.py::load_corpus`. SQLite: `load_sqlite_corpus`; выбор источника через `load_configured_corpus` (`DATA_SOURCE`). Mapping SQLite см. `docs/architecture/sqlite-data-source.md`.

1. Пропускаются пустые строки и комментарии `#`.
2. Каждая строка JSON парсится в запись `PlantDocument`.
3. Проверяются обязательные `document_id`, `plant_name`, `content`.
4. Повторяющийся `document_id` вызывает ошибку загрузки, а не молча перезаписывается.
5. Строковые `aliases` и `category` нормализуются к спискам.
6. Неизвестные дополнительные поля сохраняются в `extra`.

## 4. Разбиение на фрагменты (chunking)

Функции находятся в `backend/app/corpus.py`. Для отчёта о полноте и происхождении данных используйте `python -m backend.scripts.validate_corpus`; перед публичным запуском применяйте `--strict`.

- Из текста схлопываются последовательности пробелов.
- Текст разбивается по границам предложений/абзацев.
- Максимальный размер фрагмента — ориентировочно 900 символов.
- При переходе между соседними фрагментами добавляется overlap около 120 символов.
- Стабильный ID фрагмента: `<document_id>#chunk-001`, `#chunk-002` и т.д.
- Каждый фрагмент наследует название, научное имя, aliases, категории, источник, URL, язык и статус родительской записи.

Параметры сейчас заданы в коде chunker. При изменении размера/overlap повторно запускайте benchmark.

## 5. BM25 normalization и индекс

`backend/app/retrieval.py::tokens` приводит текст к нижнему регистру и разбивает по Unicode-буквам/цифрам. Пунктуация служит разделителем. По умолчанию:

- лемматизация/стемминг не применяются;
- стоп-слова не удаляются;
- повторяющиеся термины запроса учитываются один раз;
- индекс хранит `term -> {chunk_index: tf}`;
- для каждого chunk хранится длина `L`; `avgdl` — средняя длина корпуса;
- `N` — число chunks, `df` — число chunks с термином;
- default `k1=1.2`, `b=0.75` (из учебной презентации);
- `MIN_BM25_SCORE=0.20` отсекает слабые совпадения; BM25 score не является вероятностью.

Используемая формула:

\[
IDF(t)=\ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right)
\]

\[
BM25(q,d)=\sum_{t\in q}IDF(t)\frac{tf(t,d)(k_1+1)}{tf(t,d)+k_1(1-b+b\frac{|d|}{avgdl})}
\]

Это самостоятельная реализация базового метода из презентации, а не вызов готового поискового движка.

**Ограничение:** «мухоловка» и «мухоловки» — разные токены. Для повышения качества на реальных русскоязычных запросах можно отдельно экспериментировать с морфологической нормализацией, синонимами/alias expansion или query rewriting, но любое изменение нужно оценить на фиксированном наборе запросов. В базовой версии точная токенизация сохранена для воспроизводимости учебного алгоритма.

## 6. Индексация и обновление

BM25 index строится в памяти при создании `PlantKnowledgeService` во время старта backend. Встроенный API записи корпуса отсутствует. Чтобы применить изменения:

1. обновить `data/plants.jsonl`;
2. проверить JSONL и уникальность ID;
3. перезапустить FastAPI;
4. выполнить `python -m backend.scripts.run_benchmark`;
5. проверить источники и примеры ответов.

Не коммитьте личные, закрытые или объёмные материалы с неясной лицензией. Индексы и временные файлы не требуются в Git.

## 7. Текущее состояние данных

`data/plants.jsonl` содержит 4 авторских учебных демонстрационных текста (Dionaea, Drosera, Nepenthes, Rafflesia). Они имеют `source_url=null`, `record_status=demo_unverified` и `license_or_usage_note`, требующий проверки. Это только smoke fixture для разработки и не является верифицированной базой сведений о видах.

Для полноценной версии нужно заменить/дополнить seed-корпус не менее чем 30-ю источниками/документами в соответствии с учебной контрольной точкой; проверить лицензии, источники и содержание вручную.


## 8. Runtime SQLite corpus

В `DATA_SOURCE=sqlite` adapter читает таксономию `plants`, имена `plant_names`, категории `categories/plant_categories`, документы `documents`, описания `plant_descriptions`, записи об использованиях `plant_uses`, соединениях `plant_compounds` и местообитаниях `habitats`, а также provenance `sources`. Каждый plant row даёт taxonomy-only карточку; документ/раздел описания/использование/соединение/местообитание — отдельный документ с сохранённым источником. `plant_images` пока не сериализуются в текстовый retrieval corpus.

Excel importer `backend/scripts/import_taxonomy_xlsx.py` импортирует только таксономические колонки листа `plants` в таблицу `plants`. Пустые ячейки не стирают уже заполненные DB значения (`COALESCE`), записи с конфликтующими научными названиями откатываются. Используйте `--dry-run` и backup перед записью.

Таксономическая выгрузка не подменяет ботанические описания: пустой `description` не даёт фактов о местообитании, токсичности, употреблении, химическом составе или лечебной эффективности. `is_medicinal` — только исходный бинарный атрибут.
