# Пользовательские сценарии

## UC-01. Найти растение по названию

**Как** пользователь, **я хочу** ввести название растения, **чтобы** получить найденные сведения и перейти к источнику.

**Поток:** ввод названия → `/api/v1/ask` → BM25 → ответ/выдержки → источники. Если LLM выключена, показываются найденные фрагменты, а не имитация ответа модели.

**Критерий:** документы и источники существуют в корпусе, `source_url` не выдумывается.

## UC-02. Задать вопрос о растении

**Как** пользователь, **я хочу** задать вопрос обычным языком, **чтобы** получить краткий ответ по материалам корпуса.

**Поток:** frontend вызывает `/api/v1/ask`; backend собирает BM25-контекст; настроенная LLM формирует ответ и citations. UI показывает источники и режим генерации.

**Критерий:** ответ основан на переданных фрагментах; отсутствие информации приводит к `insufficient_data`.

## UC-03. Получить ответ при недостатке данных

**Как** пользователь, **я хочу** видеть, когда корпус не содержит подтверждения, **чтобы** не принять догадку за факт.

**Пример:** «Какое комнатное растение лечит диабет?»

**Ожидание:** отказ от медицинской рекомендации; указание, что в базе нет достаточной информации. Не выдаются инструкции по употреблению/самолечению.

## UC-04. Уточнить запрос или продолжить диалог

**Как** пользователь, **я хочу** отправить ещё один вопрос в том же чате, **чтобы** уточнить интересующую тему.

История чатов сохраняется в `localStorage`; каждый вопрос отправляется в API отдельно. Пока не реализованы серверная история и передача полной переписки как диалогового контекста LLM.

## UC-05. Предварительно распознать растение по фотографии

**Как** пользователь, **я хочу** загрузить фотографию, **чтобы** получить несколько вероятных вариантов вида и выбрать нужный.

**Поток:** JPEG/PNG upload → Pl@ntNet endpoint → top candidates → ручной выбор → поиск сведений в корпусе.

**Критерий:** без API key показывается, что функция не настроена; score не называется гарантией определения. Выбранный вид должен пройти обычный путь BM25/RAG.

## UC-06. Дополнительный поиск по инициативе LLM

**Как** пользователь, **я хочу**, чтобы модель могла сама запросить дополнительные материалы, **чтобы** сложный вопрос не ограничивался одним первичным поиском.

LLM вызывает `search_plant_knowledge` или `get_plant_profile`; backend ограничивает количество вызовов и уникальных chunks. Максимум — 10 tool calls, по умолчанию — 5.

**Критерий:** тест подтверждает вызов инструмента, возврат source refs, дедупликацию и прекращение цикла после лимита.
